# src/lib/offline — client-side offline persistence

IndexedDB storage for the offline visit flow, backed by **Dexie v4**. Runs in the browser and the Capacitor WebView (`client-only` guard — never bundled server-side). Kept deliberately separate from `src/lib/db/` (which is `server-only` Prisma).

## Why Dexie

Capacitor Preferences has a ~1MB soft key cap; Dexie/IndexedDB has no practical cap and behaves identically in the PWA and the native WebView.

## Modules

- `types.ts` — pure client-safe types + `createClientMutationId()`. Mirrors the Server Action payload shape `VisitFormValues` (`src/app/(dashboard)/visits/[visitId]/actions.ts`) and the data shapes in `src/lib/db/visits.ts`, which are `server-only` and can't be imported client-side. Keep field names in sync with those server-side types. `DraftVisitPayload` carries an optional `expectedVersion` (the revision the client last observed; replayed with the payload so a replayed `completeVisit` is version-guarded — see conflict policy below). `QueuedMutation` carries `status: pending|processing|failed|dead`, `retryCount`, `lastError`, and `nextRetryAt` (backoff schedule, persisted so a reload resumes it).
- `db.ts` — `import "client-only"`; the `poolbench-offline` Dexie schema (v1):
  - `draftVisits: "++id, &[companyId+visitId], companyId, updatedAt"` — one draft per visit per tenant.
  - `mutationQueue: "++id, &[companyId+clientMutationId], companyId, [companyId+status], [companyId+visitId], createdAt"` — unique queue entry per tenant; FIFO drain via `[companyId+status]` + `createdAt`; per-visit reads via `[companyId+visitId]`. `nextRetryAt` is an unindexed field. Schema is v2 (v2 added the `[companyId+visitId]` index; backfilled automatically on upgrade).
- `backoff.ts` — **pure, no I/O**: `MAX_RETRIES` (6), `nextDelayMs(attempt, {base=2000, multiplier=2, cap=300000, jitter=0.2})`, `computeNextRetryAt(now, attempt)`. Tunable schedule consumed only by the processor.
- `draft-visits.ts` — `saveDraft` (upsert by `[companyId+visitId]`), `getDraft`, `listDrafts` (newest first), `deleteDraft`.
- `mutation-queue.ts` — `enqueue` (mints/reuses `clientMutationId`; drops duplicates), `getPending` (FIFO, optional limit), `getPendingForVisit` (pending entries for one visit), `getByClientMutationId`, `markStatus` (status + optional `retryCount`/`lastError`/`nextRetryAt`), `deleteEntry` (single-entry removal after a successful flush), `deleteEntriesForVisit` (all entries for a visit), `getDue(companyId, {now, limit})` (pending + failed entries whose `nextRetryAt` is due or unset, FIFO — queried via the `[companyId+status]` index), `getDead` / `getDeadForVisit` (dead-lettered entries), `countEntriesForVisit` (all-status count — keeps the draft while any entry still holds unsynced edits), `deleteDeadForVisit` (drop a visit's dead entries on re-save), `retryDead` (dead → pending, retryCount 0, schedule cleared), `getStats(companyId) → {pending, processing, failed, dead}` (tenant-level counts), `getVisitStats(companyId, visitId) → {pending, failed, dead}` (per-visit counts for the sync-status badge; scoped via the `[companyId+visitId]` index, `processing` is never persisted so not tallied), `clearCompanyData` (drafts + queue, for sign-out/tenant switch).
- `sync-status.ts` — **pure, no I/O**: `type SyncStatus = "offline" | "pending" | "syncing" | "failed" | "synced"` + `deriveSyncStatus(stats: {pending, failed, dead}, opts: {online, inFlight})` + `SYNC_STATUS_META` (label + semantic tone). Precedence: failed > syncing > pending > offline > synced. Consumed by the visit form's badge/toasts.
- `sw-policy.ts` — **pure, no worker globals** (importable in tests): `isServerActionRequest({method}, {sameOrigin})` (same-origin non-GET), `buildServerActionRules()` (one `NetworkOnly` rule per non-GET method — serwist routes are method-keyed, so `method` is mandatory for a POST guard), `buildRuntimeCaching(baseRules)` (server-action rules prepended to the injected `defaultCache`; `sw.ts` supplies `defaultCache` so this module stays testable without a worker env), `APP_SHELL_PRECACHE` (stable `public/` entries: `/manifest.webmanifest` + icons), `composePrecacheEntries(manifest, shell)` (merge + dedupe by URL, normalizes string entries, tolerates absent dev manifest). Consumed by `src/app/sw.ts`.
- `processor.ts` — **queue processor** (`import "client-only"`): `drainOnce(companyId, replay, {now?, limit?, classifyError?, scheduleRetry?, replayTimeoutMs?, onDead?, onSynced?, onFailed?})`. Retry-aware sweep over `getDue`: `replay(entry)` (in-flight tracked in a module-local set, never persisted — a killed app drops it while the entry stays `pending` in IndexedDB, so a reload re-attempts it) → success deletes the entry (and the visit's draft once no entries remain) + `onSynced(entry)` → transient failure `failed` + `retryCount+1` + `nextRetryAt` + `onFailed(entry, false)`; budget exhausted (`>= MAX_RETRIES`) or `classifyError`-permanent → `dead` + `onDead(entry)` + `onFailed(entry, true)`. Guards: no-op while `navigator.onLine === false` (offline spell never consumes retry budget), single-flight (concurrent sweeps skip), and `replayTimeoutMs` (default 30s) bounds each `replay` so a hung fetch can't wedge the guard. `_resetSweepGuardForTests` is the test-only guard reset.
- `src/hooks/use-queue-processor.ts` — `useQueueProcessor({companyId, replay, classifyError?, onDead?, onSynced?, onFailed?, sweepIntervalMs?, enabled?})` — wires the processor's triggers: `useOnlineStatus` (online+hydrated), `visibilitychange` → visible (covers Capacitor WebView resume + PWA tab return), 5s sweep interval; injects `replay`/`classifyError`/`onDead`/`onSynced`/`onFailed`; `enabled: false` (used on completed/other-tech pages) silences every trigger and makes `drain` a no-op; returns `{ drain, inFlight }` — `drain: () => Promise<DrainResult[]>` for an immediate sweep (e.g. after `retryDead`), `inFlight` reflects whether a sweep is running (tenant-wide, drives the "syncing" badge state).

## Tenancy

Same invariant as the server DB layer: every read/write is scoped by `companyId`. Cross-tenant rows can't collide because both unique keys are compound on `companyId`. `clearCompanyData(companyId)` is the sign-out/tenant-switch wipe.

## Status

Write-through draft save is wired into `VisitForm` (`src/app/(dashboard)/visits/[visitId]/visit-form.tsx`): Save Draft persists to Dexie immediately (`saveDraft` + `enqueue`), then drains the queue via `useQueueProcessor` — `replay = (entry) => saveDraftAction(entry.visitId, entry.payload)` — with `classifyError` mapping Zod/access errors (deleted visit, other tech's visit) to permanent so they dead-letter immediately. A re-save calls `deleteDeadForVisit` so a newer save supersedes stale dead entries. Sync-status UI is landed: `useVisitSyncStatus` (`src/hooks/use-visit-sync-status.ts`) derives per-visit status via `getVisitStats` + `deriveSyncStatus`, renders a `SyncStatusBadge` (`src/components/visits/SyncStatusBadge.tsx`) in the actions area, and fires deduped toasts on failure transitions (dead-lettered → `UNSYNCED_COPY` "Re-save or retry", transient → "Will retry automatically"; pre-existing `failed`/`dead` state at page load is seeded and not re-toasted) and on the dirty→clean handoff when back online ("Changes synced"). The dead-letter chip now uses `sync.counts.dead` + `sync.retry()` (= `retryDead` + count refresh + immediate `drain`). `useQueueProcessor`'s `onSynced`/`onFailed` callbacks feed the hook's count refresh + toasts (dead-letter pairs `onDead` with `onFailed(entry, true)`, so the hook wires only `onFailed` to avoid double-count refreshes). Completing a visit still clears its local draft + all queued entries. SW policy is landed: `sw-policy.ts` forces same-origin non-GET requests through `NetworkOnly` (prepended to `defaultCache`) so Server Action POSTs can never be served a stale cached 200, and the SW precaches the stable `public/` shell alongside the auto-manifest with `cleanupOutdatedCaches`.

## Conflict-resolution policy (landed)

**Hybrid: drafts are last-write-wins, completions are version-guarded.**
- `saveDraftVisit` is LWW — the server ignores `expectedVersion`. Drafts are transient replaceable state; the dangerous draft case (visit completed/cancelled elsewhere) is already rejected server-side.
- `completeVisit` rejects with `VisitVersionConflictError` (409, message "This visit was updated on another device…") when `opts.expectedVersion` doesn't match the stored `version`. The guard is atomic — a conditional `updateMany` filtered on the expected revision inside the completion transaction — so a check-then-write race between two concurrent completions can't both pass. A replayed already-applied `clientMutationId` short-circuits BEFORE the guard (idempotent regardless of drift).
- The visit form keeps its known revision in a ref (`knownVersionRef`), seeded from the serialized visit. It re-bases via `useVisitSyncStatus`'s `onReplayApplied` after every successful `saveDraftAction` replay (returns `{ version }`) and re-seeds on `visit.version` prop change (a `router.refresh()` after a conflict or any refresh reflecting a status change/reassignment). `handleSaveDraft` and `handleComplete` both await the queue `drain()` first so the re-base lands before the completion's `expectedVersion` is built. All of this is load-bearing: skipping any piece falsely rejects your own next completion (false self-conflict) or, worse, loops the conflict recovery against a stale revision.
- `handleComplete` matches the conflict message on the client and shows a dedicated toast + `router.refresh()` (reload authoritative state, which re-seeds the revision) instead of the generic save-failed path.
